Decision 01 · issue #794

Can byte-identical seat briefs hit the prompt cache?

This is the architecture gate. The epic's AUTO MODE contract says: "#794 IS A HARD GATE. Its AC1 is spike S3 (~15 min): can byte-identical briefs hit cache? If NO — STOP, ask the owner, and do NOT start #799 or #795." Your framing on the issue was blunter: "if we cant get cache working, we may need to abandon executor path and go back to orchastrator with sub-agents."

Purpose

Every executor dispatch is a fresh CLI session (session_policy: "fresh"). Turn 1 writes the whole seat prompt to cache — observed 46k–132k tokens at 1.25–2× price — and every subsequent loop turn re-reads the conversation from cache (observed 1.5M–3.1M cumulative reads per dispatch). Reads are cheap in dollars, about 0.1×, but they count against the 5-hour throughput window. If a second dispatch of the same brief reused the first one's prefix, that write cost would disappear.

confirmed Why it could work at all: Anthropic's prompt cache is org-scoped and keyed on exact prompt-prefix bytes plus model — not on session identity. So cross-session reuse is possible in principle.

Method

Five dispatches of one identical brief, seat analysis, Claude lane, claude-opus-5, session_policy: fresh, run id wf2-794-cf9ff806. All five shared an identical prompt_hash, model, lane and parse_status: ok. Read cache_creation_input_tokens and cache_read_input_tokens per dispatch.

Verdict: inconclusive — and that is a finding, not a dodge

The spike cannot answer the gate question. Three defects in the experiment, all caught at review rather than by its author:

  1. The dispatches were not back-to-back. D1–D3 ran within 46 s; D4 came 8 m 31 s later. An earlier draft asserted "five dispatches back-to-back over ~40 s" — that was false. With the real timing this is two bursts: write, write, HIT then write, write, (no third). That is consistent with a warmup hypothesis, not a refutation of one.
  2. The provider inputs were not identical, even though the brief was. prompt_hash covers only req.prompt; the cached prefix spans tools plus system plus messages. Total provider input varied — about 66.4k versus 68.2k on alternating dispatches. A byte-identical dispatch was never achieved at the layer that matters.
  3. Every write landed on the 1-hour tier, not the 5-minute tier. Raw transport shows ephemeral_1h_input_tokens carrying the whole write on every dispatch and ephemeral_5m_input_tokens: 0 throughout. An earlier draft, the adapter comment and phase_executor/README.md all reasoned from a 5-minute TTL. That reasoning was wrong — and with a 1-hour TTL an 8.5-minute gap should not have expired anything, so TTL does not explain D4's miss either.
The process failure, recorded deliberately

This spike produced four successive wrong answers before review stopped it. n=1 read as "cache works". n=2 as "cache fails". n=3 as "works after a two-dispatch warmup" — and that verdict reached a commit, and would have unblocked #795 and #799 on a single anomalous data point. n=5 read as "does not work", which was also over-claimed.

The root cause of the first three was mechanical: adapters/claude_cli.py mapped cached to cache_read_input_tokens and discarded cache_creation_input_tokens, with the observation schema additionalProperties: false so nothing downstream could add it. #794's own AC2 — a measured before-and-after on cache_creation_input_tokens — was unmeasurable against shipped code. PR #811, merged as v3.115.0, landed that telemetry and deliberately shipped no verdict with it.

What a controlled re-run needs

  • A fixed inter-dispatch interval, recorded, and varied deliberately — 10 s, 2 min, 10 min.
  • At least 3 dispatches per burst and at least 3 bursts, so a warmup pattern is distinguishable from noise.
  • The full provider input captured per dispatch, not just prompt_hash — the prefix that matters includes tools and system.
  • Tier-split writes recorded, ephemeral_5m against ephemeral_1h, now that they are known to differ.
  • A session_policy: "resume" arm, since lever 2 does not depend on a byte-exact match.

Recommendation — do not retire the executor

confirmed The mechanism can hit: D3 achieved cache_write: 0. inferred The misses come from Claude Code injecting per-session bytes early in the prompt — the scratchpad path carrying the session id, and volatile git status. The brief is the tail of the prompt, not the prefix, so making the brief byte-identical cannot rescue a mismatched prefix. The controlled re-run above, capturing full provider input, would confirm or refute that.

This argues for lever 2, per-run seat session reuse — resume rather than fresh for later dispatches of the same seat within a run — over lever 1, prefix stabilization, because lever 2 never needs to win a byte-exact match. Retiring the executor on this evidence would mean discarding working, gated, audited machinery because of an experiment too loose to indict it. The next section is that machinery.

The gates earned their cost

Four real defects caught that would otherwise have shipped:

  • Rev 1's installer wrote a cache record its own reader would have rejected every time — the guard would have been permanently inactive while reading as shipped.
  • Rev 2's audit record used a new kind, but enforce.py:_validate_record raises on any unknown kind — it would have poisoned records() and reconciliation for the entire run.
  • Rev 2 promised ordered skip data on the Observation; observation-2.json is additionalProperties: false and its own description says such an addition bumps schema_version.
  • Rev 2 keyed accounts on a "default" sentinel for a null credential_ref, but _claude_env returns None there and the subprocess inherits the ambient CLAUDE_CONFIG_DIR — distinct accounts would have collapsed into one.

The three decisions

  1. AC1 says the refusal reason must be "in the receipt". No receipt can exist. enforce.check_pre runs only per-attempt (executor_routing_lib.py:853; :808 confirms none is minted before it). A total quota wall means no attempt happens, so there is nothing to attach a receipt to. Rev 3 proposes a durable quota_block audit record instead, and does not pretend that is a receipt. Amend AC1 to say "durably attributable in the audit trail"?
  2. AC2 says "Codex-lane dispatches unaffected" — your own comment makes that wrong. Codex moved to weekly-only and a free reset was burned. Confirm AC2 becomes "each pool guarded independently, and the refusal names which pool"?
  3. codex_weekly has no verified data source. The Anthropic endpoint is confirmed working by your own S1 spike, so Claude 5-hour and 7-day are implementable now. There is no equivalent verified codex usage read, and two attempts to reach credentials were denied by the permission classifier. Either (a) ship the Claude half now and file the codex pool as its own child — the pool table is generic, so codex becomes config plus one adapter, no redesign — or (b) hold #792 entirely until a codex source is spiked. Recommendation: (a). Shipping less than you asked for is your call, not the implementer's, which is why this is a blocker rather than a decision made quietly.

Still unresolved — pass-3 Highs, all verified at source

  • F1 — the wall is evaluated after _do_dispatch appends the expected call to the ledger (:3186). A walled dispatch leaves an expected call with no receipt; retrying the same correlation id is rejected as a duplicate (ledger.py:237), and a new id leaves the original permanently unreconciled (enforce.py:843). So the advertised "retryable, self-resolving" refusal cannot actually complete within the same run. Fix: evaluate before append_expected.
  • F2 — the per-dispatch quota_guard status has no durable sink. quota_block exists only when something is blocked, so an all-fail-open run looks identical to a fully-protected one. That is precisely the silent-failure class epic #756 exists to kill, inside the feature meant to prevent it.
  • F3 — the effective-config-dir identity resolves relative to process cwd, but a mutating Claude subprocess changes cwd to its worktree (claude_cli.py:158), and a value handed to a subprocess gets no ~ expansion. Poller and gate can disagree about the same account.

No branch was cut and no code was written. Design rev 3 is durable on branch docs/792-design-artifacts (8db07f4).

Decision 03 · issue #797

Your threshold instruction and the maths disagree

Your instruction, verbatim: "if 60-80 is the degredation point lets change to 55 and 75" — that is hooks/context_meter.py:84-85, DEFAULT_CHECK_IN_PCT from 35 to 55 and DEFAULT_ACT_PCT from 50 to 75.

The problem found while implementing. The meter already fires late — it fired the directive tier at 69% when the act line was 50. Raising the act line to 75 makes it fire later still, in every realistic case, even with a projection guard that fires before the crossing rather than after it:

Steady per-turn growthProjected ACT fires atVersus today's 50
1 point74%24 points later
5 points70%20 points later
10 points65%15 points later
15 points60%10 points later
20 points55%5 points later

The projection can never fire below 55, the check-in line, so 55 is the floor no matter how large the jump.

Why that is likely the opposite of what you want. Your aim is to keep sessions out of the degradation band. But the code's own recorded rationale (context_meter.py:76-85) says the binding constraint is something else:

"At 35% of a 1M window a session has ~650k tokens in hand to finish its phase and hand over properly; at 70% it has 300k and is already choosing what to drop."

That argument is about room left to write a good handoff, not about where quality degrades. The two pull in opposite directions. AC1 already anticipated exactly this: "Thresholds are 55/75 (or the owner-approved alternative if the overshoot fix changes the calculus)." The overshoot analysis changed the calculus. Step-4 review returned shippable: no — 4 High and 1 Medium — with this finding flagged ambiguous.

Recommendation: fix the late-firing first — #729 and #734 are the meter-reliability children already in this epic — then retune on a meter that fires when it says it does. Setting 55/75 on today's overshooting meter would likely push real handoffs past 75%, inside the degradation band, with less room to hand over well.

Why old herdr panes stopped closing

confirmed #758 merged 2026-07-31 at 01:13 (158b6ee2, PR #773) and made goal-reading trust only rows stamped sentinel: true. That was deliberate, and it is a prompt-injection boundary: without the stamp, structured content pasted into a transcript could forge a goal_status row and spoof "already cleared". That was a real bypass, found during #758's own review.

The side effect nobody caught: Claude Code stamps sentinel: true when it arms a goal, but not when the Stop hook evaluates one. So after any evaluation the newest row is unstamped, the fail-closed validator refuses, and pane-handoff teardown exits before it closes anything. Measured 2026-08-01: 53 of the 120 most recent transcripts are in the refusing state.

#802 looked like the fix, but PR #803 (26f865ef) changed only the wording of the refusal — 4 files, mostly the skill doc and its test, with the behaviour untouched. #782 — open, zero comments, and not in this epic — is the real fix, and it is the best small follow-up candidate on the board.
