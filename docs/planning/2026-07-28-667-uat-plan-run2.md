## The headline: the watcher fires

**W2–W7 all moved BLOCKED → PASS.** That is epic #684's exit criterion 1, and it is the whole reason
the epic existed. A throwaway pane running `claude --permission-mode default` was driven to a real
"This command requires approval" prompt; it reached `agent_status: blocked`; and the watcher —
`pane_watch_lib.py watch --source poll --sender-cmd 'cat >> …'`, so nothing paged the owner — delivered:

```
herdr: w1:pD3 [claude] is blocked — waiting on you (w1 w1:t15)
```

Then, over 47 further polls of the same blocked pane, it delivered nothing more (W3). Esc cleared the
prompt and a second gated command re-blocked it; the heartbeat went to `notified: 2` (W4). The body
carries pane id, agent, workspace and tab and no prompt text at all (W5). The heartbeat advanced
monotonically with `poll_failures: 0` throughout, carrying the input layer's own counters (W6). And a
watcher started fresh against an already-blocked pane notified within three polls via the startup
sweep (W7).

**The one number worth staring at: `revision` did not advance across `working → blocked`.** It read 3
before and 3 after. That is #679's *second* root cause — the one the issue did not describe and only a
live run could find — and it is exactly why the dedup key had to become `state_change_seq`. A separate
observation in this run corroborates it: `herdr agent prompt` returned an agent object carrying
`state_change_seq: 2217`, the field the `pane.updated` event never carried.

## L2 and H3: the blocker moved, and that is the finding

Exit criterion 2 hoped L2 and H3 would reach `project_switched`. They do not — but **for a different
reason than run 1**, and the difference matters:

| | run 1 | run 2 |
|---|---|---|
| L2 | INCONCLUSIVE — `project_switched` never completed (#682's bug) | BLOCKED — the ladder refuses at step 0 |
| H3 | INCONCLUSIVE — same evidence | BLOCKED — same |

Run 2 never gets as far as `project_switched`, because `launcher_lib.py handoff` refuses first:

```
no handoff: no durable launcher armed (launch mode 'herdr')
```

`fresh_session_available` requires the **caller** to assert `--launcher-armed` *and*
`--fresh-launch-supported`, and `launcher_lib.py:2156` says in as many words that absence must not read
as support. This session can genuinely spawn a pane, so `--fresh-launch-supported` would be true. It has
**no durable launcher armed**, so `--launcher-armed` would be a false assertion made purely to get past
a guardrail — and that is the one move the operating rules forbid outright. So it was not made, and the
check is recorded BLOCKED with the reason rather than passed with a lie. The predecessor session reached
the same wall and made the same call.

**What #682 demonstrably did fix** is visible in the contract rather than inferred: `--project` is now
**required** on the `handoff` subcommand, which is why a bare `/rawgentic:switch` — which enters list
mode and waits for a human — can no longer ship in a resume prompt.

H4, H5 and C7 sit behind the same gate: H4 and H5 need a completed six-step ladder to authorise
retirement, and C7 needs the same handoff path. Recorded on each rather than collapsed into one entry.
H6 independently confirms the refusal machinery itself is right — `teardown_allowed` refuses and *names*
the unmet step.

## Findings this run produced

1. **The startup-sweep notification is not counted.** W7's watcher delivered the body while its
   heartbeat reported `notified: 0` — `write_heartbeat` only counts `report['notified']` and the sweep
   path passes none. Delivery is proven by the body; the counter under-reports. Worth fixing, because
   this heartbeat is the thing an external observer is supposed to trust.
2. **A cosmetic duplication in the #687 advisory.** It renders "A step boundary was just recorded
   (a workflow step boundary was just recorded)" — a consequence of making the seam reason generic to
   close the injection channel. Harmless, but the owner reads this text.
3. **P2's wording is superseded.** "revision advances" is refuted; the check should be reworded to
   `state_change_seq` before run 3, or it will keep asking a question the system no longer answers.
