#765 Design Bake-off — Wiring Map

How the WF2 Step-3 head-to-head works, what is wired today, and exactly what stands between it and "runs every child".
Verdict: not fully run-ready — exactly ONE issue away (#775). The head-to-head mechanics are real and were live-proven twice today (two models concurrent, glm judge, winner's exact bytes out, both candidates recorded). What's missing is plumbing, not mechanics: the judge environment is hand-prepared per session, and no real child has used the round as its actual design step yet. Per your call it ships OFF by default behind a flag; #775 hardens it to run-ready.

01 · The on/off flag (shipped, default OFF)

Per-project, in .rawgentic_workspace.json: "designBakeoff": {"enabled": true} — absent, malformed, or unreadable always means OFF (Step 3 keeps today's mechanism and logs a one-line skip). Nothing runs, nothing costs tokens, unless a project opts in.

The workflow checks it with: python3 hooks/bakeoff_policy.py design-round-enabled --workspace <ws> --project <name> → exit 0 on, 1 off. WIRED + TESTED

02 · The flow when it's ON

Design brief goes in WIRED

design-round --prompt-file <brief> --run-id wf2-<issue>-<session> --correlation-id <issue>-s3-design — identity is REQUIRED, so every round is attributable to its run (a missing id refuses, exit 2).

Two models, head-to-head WIRED · LIVE-PROVEN ×2

gpt-5.6-sol
codex quota pool · 8.3s / 25.7s live
claude-opus-5
claude quota pool · 10.7s / 26.8s live

Genuinely concurrent (separate pools — tokens, not wall-clock). A crashing candidate is isolated; it can never abort the round or win.

glm-5.2 judges WIRED · ENV IS MANUAL (#775)

Drafts are anonymized and shuffled (the judge can't tell whose is whose), scored on the vendored design rubric, winner picked. The catch: the judge needs the API key + zhipuai SDK — today that means running under the workspace bench venv with the key file sourced. Fail-loud if missing (exit 3), never silent — but it won't self-bootstrap yet.

Winner's exact bytes come out MECHANICALLY WIRED (#775 adopts)

--winner-out writes the winning draft byte-for-byte — today's review wave caught the CLI discarding it (your "doesn't feel plumbed in" instinct was correct). Fixed and tested — but no real child has consumed it as its design draft yet.

Both sets of information recorded WIRED

Raw record (both candidates' full text) → local gitignored sink. Sanitized record (models, timings, scores, usage, prompt/rubric hashes — no payloads, no paths) → --evidence-out, committable, locked by a fail-closed test. Live proof: docs/measurements/bakeoff-765-design-round-evidence.json

Workflow moves on WIRED

Step 3 continues with the winner. Judge down? Interactive = stop loudly (exit 3). Headless = the incumbent (opus) wins with a judge_degraded flag on the record — a degraded round can never pass as clean evidence.

03 · Wired today vs not yet

Wired & tested (this PR)

  • The on/off flag, default OFF (designBakeoff.enabled)
  • Run-identity plumbing — every round + every candidate carries the run's id
  • The workflow-callable CLI the Step-3 prose names verbatim
  • Concurrent head-to-head on separate quota pools (live ×2)
  • Anonymized glm judging + degraded-round flagging
  • Winner's exact bytes via --winner-out (atomic)
  • Raw + sanitized dual recording; committed live evidence, fail-closed guard
  • 10 review-wave hardenings (strict sanitizer, sink containment, fail-loud everywhere)

Not wired yet → #775

  • Judge env self-bootstrap (key file + zhipuai interpreter) — manual per session today
  • First real child running the round as its actual Step-3 design step
  • Winner bytes → the child's design draft, exercised end-to-end in a live run
  • Per-run evidence naming convention + run-record hook (makes value measurable)
  • The default-ON decision — owner-gated, brought with measured evidence
