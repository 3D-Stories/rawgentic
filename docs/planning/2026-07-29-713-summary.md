# #713 in plain words: why a long run burned its whole window instead of handing off

**The short version.** Your session was told "keep going" ten times and "you're nearly full" twice —
and the "you're nearly full" message could never arrive at the moment the "keep going" decision was
made. We fixed the timing, and found two more bugs on the way, one of which meant a whole part of
the warning system had never worked at all.

---

## 1. What broke, twice, in one day

Two of your runs failed at opposite ends of the same gap.

| Run | What it did | What went wrong |
|---|---|---|
| **lumenquire** | Shipped 14 PRs, took the e2e suite from 30 pass / 1 fail to 40 pass / 0 fail | Rode a 1,000,000-token window to **~98% full** and never handed off. You had to do it by hand. |
| **thewanderinginn** | Stopped at a clean task boundary, wrote a proper handoff file | Then **asked permission** to start the successor — *"say the word and I'll run it"* — and sat idle overnight because nobody was awake to say the word. |

Both end the same way: no successor, and a human needed.

The cost in the first one is visible in the quality. Early passes each got reproduce-first,
red-before-green and a committed guard. Pass 6 shipped with no guard. Pass 8 finished 1 of its 6
issues. The closeout was never started — because starting it at 98% would have meant inventing
answers, and it correctly refused to. **The only reason it faced that choice is that it was at 98%.**

---

## 2. Why it happened

`/goal` decides whether to keep going at a moment called **Stop** — the instant a turn ends.

The context meter was not listening at that moment. It was registered on two other events, both of
which happen *in the middle* of a turn. So its warning always arrived mid-turn and was already old
news by the time the "keep going?" decision was made.

In your run the Stop hook fired about **ten times**. Not one of those firings had a handoff
instruction available to it.

**This was a timing problem, not a loudness problem.** The message was fine. It just never spoke in
the room where the decision was made.

---

## 3. The three bugs

### Bug 1 — the meter was never in the room (the reported one)

Registered on the wrong events. Fixed by adding the `Stop` event.

### Bug 2 — one of the meter's two arms had never worked, ever

Found while researching Bug 1, and this one is worse than it sounds.

A hook talks to the model by printing a small piece of JSON. There are two possible shapes. The
meter used the **wrong shape** on one of its two events — so on that event, Claude Code silently
threw the message away. No error, no warning, nothing.

That arm had been dead since it shipped. The meter had been running on **one** working arm this
whole time.

We proved it by registering only that shape, on its own, and asking the model what it could see. It
replied **`NONE`**.

### Bug 3 — telling the model to hand off does not make it hand off

The most useful thing we learned, and it changed the fix.

We injected a "you're nearly full, hand off now" message into a real running goal loop. The model
read it, **flagged it as a possible prompt-injection attack, and refused to obey it** — while still
reporting that it had seen it.

That is correct behaviour. Text injected by a hook is *data*, not orders. It is the same defence
that stops a malicious file telling your agent what to do.

**So the fix could not be "order the model to hand off".** It had to be something the model treats
as trustworthy.

---

## 4. What the proof-of-concept actually proved

Five experiments against a real Claude Code, all committed so they can be re-run.

| # | Question | Answer |
|---|---|---|
| 11 | Can the meter speak at `Stop`? | **Yes** — and doing so **forces one extra turn**. The hook fired twice and the session took two turns for one prompt. |
| 12 | Does adding our hook break `/goal`? | **No.** Both hooks fired every turn, the goal ran and completed normally. |
| 13 | If our hook crashes at `Stop`, does the turn break? | **No.** Broken hook, garbage output, exit code 1 — session finished normally. |
| 14 | Which message shape works? | **Only the nested one.** The other is silently dropped. (Bug 2.) |
| 15 | **Does a handoff actually satisfy a `/goal`?** | **Yes** — proven, see below. |

Probe 15 is the important one. We armed a real goal that said *"finish the work, OR record a
handoff — a recorded handoff satisfies this goal"*. The session wrote the handoff, never did the
work, and **the goal completed**. The judge's own words:

> This recorded handoff satisfies the goal condition explicitly stated in the stopping criteria.

So the sentence **"a handoff satisfies a loop goal"** is not wishful thinking. It is literally how
the judge behaves. That is the one channel the model trusts — because it is *your* goal text, not
injected text.

---

## 5. What we built

| Change | Why |
|---|---|
| Meter now also listens at **Stop** | So the warning exists when the "keep going?" decision is made |
| Stop arm speaks **only inside a loop**, and **only at the 70% tier** | Speaking at Stop forces an extra turn. Inside a loop that costs nothing (it was continuing anyway). Outside one it would hijack a turn you never asked for. |
| Every message uses the **nested shape** | Fixes the dead arm (Bug 2) |
| Deliveries recorded **per channel** | Otherwise the mid-turn warning would eat the record and silence the new Stop warning — reproducing the original bug through its own fix |
| The message now says **"a handoff SATISFIES a loop goal"** | Stated as a *fact*, not an order, because orders get refused (Bug 3). And it is true (probe 15). |
| The 60% message says **"write the resume prompt now"** | The old one said "look for a seam" and named nothing to produce, so nothing got written until there was no room to write it |
| The 70% message names **`/rawgentic:pane-handoff`** | The old one named `clear-prep`, which prepares the payload but **starts no successor** — exactly the overnight failure |
| `pane-handoff` now says **run it, don't offer it** | Your decision, 2026-07-29. The "offer it unprompted" wording was the actual cause of the overnight stall |
| One safety check before an **unprompted** handoff | It verifies the reminder came from this session's own hook. Without it, any text imitating a meter message could make an agent spawn a session and clear a guard |

---

## 6. What it costs, honestly

**At most one extra turn**, once per session. If the goal finishes at the exact moment the meter
first speaks at Stop, our message becomes the thing that continues the turn.

That extra turn carries "you're at 70%, hand off, here's how" — which at that point is the behaviour
we want. So we accepted it deliberately rather than designing it away.

An independent reviewer (a different AI model) checked the design and found **7 problems**, then
checked the code and found **4 more**. Most became changes. Two suggestions were declined in
writing, with reasons, so the trade-off is on the record rather than buried.

---

## 7. What is still not proven

- Nothing was tested on an **older Claude Code**. The Stop message is a recent capability; on an old
  version it degrades to silence rather than breaking anything — but that is reasoned, not measured.
- The 8-continuation safety cap was never pushed to its limit.
- Neither original failure has been **reproduced end to end after the fix**. That needs another long
  real run — which is the honest limit of everything above.
- Probe 15 used one wording, once. It shows the mechanism works; not that every phrasing works.
