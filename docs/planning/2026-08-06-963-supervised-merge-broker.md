# #963 — Supervised-merge broker: design

Date: 2026-08-06. Issue: [#963](https://github.com/3D-Stories/rawgentic/issues/963). Epic lineage: #871 → #947 §1a (deferred integration, discharged here). Author: claude-fable-5 (WF2 Step 3). Status: draft for Step 4 gate.

## 0. Problem in one paragraph

Epic #871 shipped a full authority-and-claims core with zero live callers: `authority_permits`, `route_for`, and all five `supervision_claims` functions have no production caller (verified by trace, 2026-08-06); `evaluate_campaign`/`consult_permitted` have exactly one (`consult_check`). Merges are executed by skill prose running raw `gh pr merge` (`skills/implement-feature/references/step-14.md:35`); `hooks/` contains no merge execution. Meanwhile the #947 Step 11 review found (dispositions gate 11, findings 1/4/7, all deferred) that a DELETED `.supervision.json` reads as `absent` → attended → `authority_permits` returns True for every action kind. This design (a) closes the deletion hole first, (b) builds the one broker command, (c) cuts the prose call sites over, (d) adds decision telemetry.

## 1. Approaches considered

**A. launcher_lib subcommand + read_state-level marker mapping (CHOSEN).** Broker as `python3 hooks/launcher_lib.py broker-merge …`; the durable marker is consulted inside `supervision_lib.read_state`, mapping declared-then-deleted to the existing `"invalid"` load status so every consumer fail-closes with no per-consumer edits.
- Pros: one-helper-one-home (campaign machinery, injectable runner, and the `classify_issue_state` evidence probe already live in launcher_lib); the `"invalid"` mapping makes the existing docstring at `supervision_route.py:287-289` ("invalid (corrupt/deleted-mid-session)") true instead of aspirational; zero changes to `authority_permits`, `consult_check`, or claims sentinels — they already deny on invalid (`supervision_route.py:298-304`; `supervision_claims.py:125,131`).
- Cons: launcher_lib grows past 6800 lines; `"invalid"` loses the deleted-vs-corrupt distinction in the view (mitigated: stderr warning at read time + telemetry reason string name the marker).

**B. New `hooks/supervision_broker.py` module + a fourth load_status `"deleted"`.**
- Pros: launcher_lib stays smaller; `"deleted"` is self-describing in every downstream surface.
- Cons: the broker needs launcher_lib anyway (issue probe, runner idiom, locked driver-state read) — a new module either imports 6756 lines lazily or duplicates them; a fourth status value forces an audit of every `load_status` consumer (8 call sites) and any missed one silently treats `"deleted"` as not-"valid"-but-also-not-"invalid" with undefined semantics; new hook modules auto-enroll in the smoke suite (fine, but one more surface).

**C. Marker checked only at `evaluate_workspace`/`authority_permits` (narrow blast radius).**
- Cons (disqualifying): `supervision_claims._current_supervision_revision` calls `read_state` directly (`supervision_claims.py:129-134`), so a view-level check leaves claim minting open under a deleted file (`absent → 0` = a legitimate never-declared revision); `installs_forbidden`/`scanner_bootstrap` would likewise stay open. Exactly the class of missed-consumer hole this issue exists to close.

Choice: **A**. Effort M-L. Risk: fail-closed regressions on attended workspaces — bounded by the back-compat rule (no marker file → behavior byte-identical) and the test plan (§8).

**Cross-model provenance (peer consult, gpt-5.6-sol via review_runner, 2026-08-06; own draft written first, blind).** The peer proposed a new `hooks/supervision_merge.py` module with an immutable never-cleared marker at `<workspace>/.rawgentic/supervision/`. Adopted from the peer: (1) **idempotent broker re-runs** — an existing claim with the same execute-once identity resumes (pending → continue; executing → reconcile first; executed → rc 0), so crash recovery and the parked→human→re-run path never refuse or double-merge; (2) **PR-state evidence probe recording the merge SHA** (`gh pr view --json state,mergeCommit` shape) rather than the issue-state probe alone; (3) **one structured JSON result line on stdout** (`status`, `reason`, `claim_id`, `merge_sha`, `next_action`) for prose and telemetry symmetry; (4) the **legacy-migration note** in §2. Declined with reason: the separate module (the broker needs launcher_lib's probe + runner either way — a new "GitHub adapter" abstraction is an unrequested layer); the immutable marker (deleting an ATTENDED record would then read invalid and brick installs+merges workspace-wide — a fail-closed outage for zero security gain, since deletion during attendance widens nothing); the audit-outbox/event-drain machinery (its own risk list concedes the lock-order complexity — the simple fail-closed pre-execution append achieves the same security property); the rich exit-code vocabulary 20/21/30/31/40/41/42 (house idiom is small ints; reasons ride stdout JSON + telemetry). The inline brainstorm pass (deep-reasoner) independently converged on Approach A and contributed the marker-specific denial diagnostics (§3, rc 12 reason text).

## 2. Component 1 — the durable declaration marker (AC2, lands first)

**Marker file:** `<workspace>/claude_docs/.supervision.declared.json` — a sibling of `.supervision.json`, same directory, written atomically. Content:

```json
{"schema_version": 1, "declared": true, "revision": 4, "state": "away", "ts": "2026-08-06T22:00:00Z"}
```

**Lifecycle (all writes inside the already-held supervision-file lock — `supervision_admin.py` is the sole writer):**
- `declare()` writes the marker (`declared: true`, the new revision, the declared state) **before** persisting the state record, both under the lock taken at `supervision_admin.py:189-190`. Crash between the two writes → marker live + state absent → reads as invalid → deny. Fail-closed, recoverable by re-declaring or `mark_attended`.
- `mark_attended()` writes `declared: false` (keeps the file — a present-but-false marker is a positive "attended" record) in the same lock hold that persists the attended record. Deleting an attended record afterwards reads as never-declared → attended, which widens nothing (attended already permits everything).
- `mark_transport_verified()` does not touch the marker (it edits an attended record).

**Read side (`supervision_lib.read_state`) — the marker is consulted on EVERY read, not only when the state file is absent (Step-4 pass-1 Critical: the absent-only variant left a crash between declare's two writes reading as a stale VALID attended record, permitting everything while the owner is away).** The consistency rule, applied after the state file loads (or fails to load):
- no marker file → today's semantics exactly (state governs; absent → never-declared → attended) — back-compat, all existing workspaces unchanged;
- marker present but unreadable/corrupt/oversize → `"invalid"` + stderr, regardless of the state file — fail-closed on a security boundary;
- marker parses with `declared: false` → state governs (a deleted ATTENDED record reads absent → attended, which widens nothing);
- marker parses with `declared: true` → `Loaded({}, "invalid")` + one stderr line naming the marker, whenever ANY of: the state file is absent (declared-then-deleted); the state record says `attended` (declare crashed between marker and state writes — the pass-1 Critical); or `state.revision < marker.revision` (stale pre-declare record). A valid away/sleeping record at `revision >= marker.revision` passes through unchanged.

Hot-path cost: one additional small capped file read per `read_state` call (the same discipline as the state read). The no-workspace-root branch (`supervision_lib.py:165-167`) is unchanged — no workspace context means no marker to consult.

**Write ordering (revised for the cross-check):** `declare` writes the marker (`declared: true`, revision N+1) FIRST, then the state — a crash between now reads invalid (marker true + attended-or-stale state), never attended. `mark_attended` clears the marker (`declared: false`, revision N+1) FIRST, then writes the attended state — a crash between leaves the old away/sleeping record governing (restrictive, no widening), and re-running `mark_attended` completes recovery.

**Recovery revision rule (owner decision 2026-08-06, AskUserQuestion at the Step-4 breaker):** when the state file is absent and a live marker exists, the next `declare`/`mark_attended` derives its revision as `marker.revision + 1` — never the absent-state default of 0 — so the revision fence and any claims bound to pre-deletion revisions stay coherent. The full-reset alternative (cancel all claims on recovery) was declined by the owner.

**Ship-time migration (`supervision_admin.py bootstrap-marker`, Step-4 pass-1 High; self-healing added pass 2):** a live declaration made BEFORE this ships has no marker, and waiting for the next admin write leaves the deletion hole open in production. Two layers:
1. **Broker self-heal (load-bearing):** on every `broker-merge` invocation, when the state record is VALID and no marker exists, the broker writes the matching marker under the supervision lock BEFORE evaluating — so the first broker use migrates the workspace unprompted, and a skipped manual step cannot silently preserve the legacy fail-open behavior. `declare`/`mark_attended` writes migrate it likewise.
2. **`bootstrap-marker` admin subcommand (belt and suspenders):** under the supervision lock, read the state; a valid record → write the matching marker (`declared = (state != "attended")`, the record's revision); absent or invalid → report and write nothing. Operational step recorded in docs/supervision.md and this PR: run once on this workspace immediately after merge + plugin reinstall.
The reviewer's stronger machinery (per-workspace migration registry + broker activation fence) was declined: this is a one-workspace deployment, the self-heal closes every future window mechanically, and a plugin has no install-time execution hook to anchor a registry to.

**Why clear-on-attend rather than an immutable ever-declared marker (peer disagreement, resolved):** the marker means "a declaration is live NOW", not "ever declared". Deleting an ATTENDED record widens nothing (attended already permits everything), so denying there is a pure fail-closed outage. The crash windows are analyzed under "Write ordering" above — both directions fail restrictive, never permissive.

**Why this closes findings 1 and 4 at every consumer at once:** `authority_permits` denies invalid (`supervision_route.py:298-299`); claims revision becomes the `-1` refuse-sentinel (`supervision_claims.py:125,131`); `consult_check` denies via the invalid view; `installs_forbidden` returns True on invalid (`supervision_lib.py:364`); `evaluate_campaign`'s governed-ids narrowing no longer silently disables (invalid view denies everything anyway).

**Finding 7 (deleted campaign driver-state) — the governed-campaign hardening:** for MERGE, a missing driver-state already denies (policy `{}` → no grant). The residual widening is consult-only: a deleted restriction-bearing driver-state file falls back to the workspace consult grant. Close: in `evaluate_campaign`, when the supervision record is valid AND `campaign_id ∈ governed_campaign_ids` AND the driver-state file is missing, treat it as corrupt (deny merge + zero the consult grant), because a governed campaign is a positive registration that state is expected to exist. Non-governed campaigns keep today's pass-through.

## 3. Component 2 — the broker command (AC1)

**Home:** `hooks/launcher_lib.py`, subcommand `broker-merge`, following the three-part registration pattern (handler `_cmd_broker_merge`, parser block, dispatch chain entry — exemplar: `record-child-outcome` at `:5189-5237`, `:6621-6632`, `:6701-6702`).

**CLI:**
```bash
python3 hooks/launcher_lib.py broker-merge \
  --pr <n> --issue <n> --campaign <campaign-id> --project-root . [--repo <owner/name>]
```
`--repo` defaults via the existing `repo_from_git`. All `gh` calls go through the injectable `runner` (`_default_runner`, `launcher_lib.py:1588-1590`) — the established testability idiom. The broker never constructs a `CampaignView` (AST guard) — it calls `evaluate_campaign`.

**Sequence (telemetry points marked "T"):**
0. **Marker self-heal:** state record VALID + no marker → write the matching marker under the supervision lock (`bootstrap_marker`, §2) before anything else.
1. `evaluate_campaign(workspace_root, campaign_id, project_root, now)` — workspace root by the existing walk-up (`_supervision_view_for` idiom, `:4576-4591`).
1b. **Target binding (Step-4 pass-1 High): the authorization must bind to THIS pr/issue/repo, or a grant scoped to one campaign authorizes any merge.** Before the authority check:
   - **Repo binding (pass-3 High, adopted):** the effective repo must equal the project's configured canonical `repo.fullName` (`.rawgentic.json`, already loaded by every WF2 run) — an explicit `--repo` that differs is rc 12, and cross-repository references can never pass.
   - Read the campaign's driver state (`_locked_state_read`) and record its content hash; require `--issue` to be one of the campaign's children (the exact driver-state field named at T5 RED from `driver_lib`'s schema).
   - Verify the PR↔issue linkage live — `gh pr view <pr> --repo <repo> --json closingIssuesReferences,body,title`: `--issue` in `closingIssuesReferences`, OR a **line-anchored** `(Closes|Part of) #<issue>` match in the body/title (the deliberate PR-body convention slot — an anchored match rejects quoted or mid-sentence historical mentions). **Multi-PR children are legitimate: repo convention says only the LAST PR closes, earlier ones say "Part of", which does not populate `closingIssuesReferences` — verified live on PRs #956/#958.** The binding defends against caller confusion, not a malicious author — the PR author is the campaign's own child run, the same trust domain as driver state. The reviewer's stronger alternative (persist an exact `{repo, issue, pr}` tuple per child in driver state and authorize only that) needs a new pre-merge PR-registration surface in the driver — deferred to the PreToolUse hardening follow-up the issue names, where it belongs with the other enforcement work. Any mismatch or missing evidence → rc 12 (binding failure), nothing executed.

**Canonical claim identity (pass-2 High, internal consistency):** ONE tuple everywhere — `{campaign, issue, repo, pr, squash, delete_branch}` — used for minting, conflict detection, resumption, and telemetry, persisted as immutable claim metadata. §3 step 3 and this step share this definition; no second identity exists.

**Stale-authorization recheck (pass-2 High, TOCTOU):** the driver-state content hash from this step is stored on the claim; immediately before the `gh pr merge` call (after `begin_execution`), the broker re-reads driver state, re-runs `evaluate_campaign` + `authority_permits` — a changed hash or a now-denying authority aborts with rc 12 and a `stale-authorization` reason. The reviewer's hold-the-lock-through-merge alternative was declined: holding a file lock across a network call that can take minutes blocks every other supervision operation; the recheck shrinks the window to milliseconds without that cost. **Revocation semantics (pass-3 Medium, stated):** authorization is evaluated at decision points — binding, minting, and the final recheck — never mid-flight; a revocation landing after the final recheck takes effect at the NEXT decision point (the GitHub merge API has no cancellation), and the executed claim + telemetry record which authorization the merge ran under. This is a named, accepted bound, not an oversight.
2. `authority_permits("merge", view=view)` → T-authority line (permitted/denied + reason: state, grant, override, load_status). **Denied → rc 12, nothing executed.**
3. `claim_action(action_kind="merge", action_target=<repo>#<pr>, params digest of the canonical identity `{campaign, issue, repo, pr, squash, delete_branch}`)` → T-claim minted. **Re-run transition table (owner decision 2026-08-06, pass-2 breaker):**
   - `pending` → continue from step 4;
   - `executing` (incl. durably-parked: a parked claim STAYS `executing` with parked metadata) → reconcile (step 6 ambiguous path — probe first, never a blind second merge) before any new `gh` call;
   - `executed` → terminal forever → rc 0 with the stored merge SHA;
   - `cancelled` → never blocks: the re-run performs FRESH target binding and a FRESH authority evaluation, then mints a new claim, with a `reopened` note in telemetry;
   - only a genuine refusal (revision fence, ClaimError) → rc 12 with the reason.
4. `begin_execution(claim)` → T-claim executing. **The pre-execution telemetry appends (T-authority through T-executing) are fail-CLOSED: if a line cannot be recorded, the broker aborts before any side effect** — an unmeasurable outward action is the exact failure this issue exists to prevent.
5. `gh pr merge <pr> --repo <repo> --squash --delete-branch` via the runner, bounded timeout.
6. Outcome:
   - rc 0 from `gh pr merge` → **confirm before recording (Step-4 pass-1 Medium):** run the PR-state probe (`gh pr view <pr> --json state,mergeCommit`); require `MERGED` plus a merge-commit oid; `mark_executed` stores that `merge_sha` in the claim → T-claim executed → **broker rc 0** with the SHA in the stdout JSON. A success the probe cannot confirm is treated as the ambiguous path below — never recorded unconfirmed.
   - Unambiguous failure (non-zero rc with a definite error, e.g. review-required refusal) → `reconcile_claim` with the evidence probe → probe says `confirmed_open` → claim cancelled → T-reconciled(cancelled) → rc 12 with gh's stderr as the reason.
   - **Ambiguous outcome** (timeout, transport error, unknown state — the GitHub merge API has no idempotency key): `reconcile_claim` with a **PR-state evidence probe** (peer-adopted; `gh pr view <n> --repo <r> --json state,mergeCommit` via the runner — PR `MERGED` + mergeCommit oid, not the issue-state proxy) — `MERGED` → resolve → `mark_executed` with the merge SHA → rc 0; `OPEN` → ONE internal retry of step 5, then re-probe; still ambiguous or `unknown` → **park** → T-parked → rc 13, claim left for a human, safely re-runnable (idempotent resume above).
   - **Result surface (contract narrowed, owner decision 2026-08-06):** one JSON line on stdout on every HANDLER exit — `{"status", "reason", "claim_id", "merge_sha", "next_action"}` — so prose branches on rc and humans read the reason (denial reasons are marker-specific when the marker caused the invalid state: "declared-then-deleted; run /rawgentic:back or re-declare"). Argparse usage errors (rc 2 before the handler runs) keep the standard stderr message, matching all 17 existing launcher_lib subcommands.
   - Post-execution telemetry failures (T-executed, T-reconciled) are fail-LOUD-continue (stderr): the merge is already real and the claims file carries the authoritative state — aborting would only desynchronize.

**Exit codes** (next free in launcher_lib is 12): `0` merged-and-recorded · `2` caller/usage error (LauncherError convention) · `12` denied or refused pre-execution (authority denial, target-binding failure, claim refusal, strict-telemetry append failure, confirmed-open merge refusal — the distinct machine-readable reason rides the stdout JSON + telemetry) · `13` parked-ambiguous (human inspection required; claim parked; the command is idempotently re-runnable). `--repo`, when passed explicitly, is validated against the `owner/name` shape before entering runner argv (list-form argv already prevents shell injection).

**AC3 (attended pass-through):** `authority_permits` returns True for a valid attended record (`supervision_route.py:300-301`) — an attended campaign merge flows straight through, now with execute-once claim protection. Non-campaign merges never reach the broker (AC4 conditions the cutover on an active campaign) — byte-identical raw path.

## 4. Component 3 — decision telemetry (AC5)

**Store:** `<workspace>/claude_docs/supervision-telemetry.jsonl` — beside the supervision state, outside the session-notes trimmer glob (the `decision_log.py:11-16` durability argument), uncommitted, survives session boundaries on disk. A committed store was rejected: run-records ride the PR pre-merge (#888), but broker decisions happen AT merge time, after PR content freezes — a committed store would always lag one PR.

**Appender:** `supervision_telemetry.append_event(workspace_root, event: dict) -> None` in a NEW tiny module `hooks/supervision_telemetry.py`, byte-for-byte the `decision_log.append_record` pattern (`decision_log.py:97-137`): `O_CREAT|O_WRONLY|O_APPEND` 0600, `flock(LOCK_EX)`, torn-tail newline repair, single buffered write loop, `fsync` + dir-fsync. A new module rather than `supervision_lib` because `fcntl` is NOT on the supervision_lib import allowlist (`tests/hooks/test_supervision_lib.py:513-516` — allowed: argparse, collections, dataclasses, datetime, json, os, re, stat, sys, typing) and that allowlist protects the per-tool-call context_meter read path. Emitters (supervision_claims, consult_check, the broker) import it lazily. The module is stdlib-only (os, fcntl, json), no argparse (smoke suite auto-enrolls it for clean-env import only). Raises on failure; each CALLER decides the fail mode (§3 step 4 vs 6).

**Emission points** ("every authority decision and every claim transition" = every live decision path):
- claims transitions: inside `supervision_claims` at each state write — minted / executing / executed / cancelled / reconciled(resolve|retry|park). **The functions gain `telemetry_mode="strict"|"best_effort"` (default `best_effort`) — Step-4 pass-1 High: without it, a swallowed append failure inside claims would let the broker merge without the transition record it believes is fail-closed.** `strict` re-raises the append failure to the caller; `best_effort` prints one stderr line and continues. The broker passes `strict` for `claim_action` and `begin_execution` (abort before any side effect, rc 12, reason `telemetry-unavailable`); the `back` skill's `cancel_claims` and all post-execution transitions stay `best_effort` (the merge is already real; the claims file carries the authoritative state).
- authority decisions: at the two call sites with workspace context — the broker (merge; the T-authority append is strict, same abort semantics) and `consult_check` (consult, best_effort).
- **Crash-gap self-repair (pass-3 High, adopted-modified):** claim state and telemetry are two files with no atomic commit; a strict-mode abort can leave a claim transition without its line. The claims file is the AUTHORITATIVE lifecycle record — a telemetry gap loses one measurement line, never authority. Mitigation: every broker resume emits a `resumed` line carrying the claim's current state, so any crash-window gap self-heals at the next touch. The reviewer's `telemetry_pending` outbox inside the claims file (atomic commit + drain + delivered-mark + failure-injection matrix) was declined a second time: the pass-2 peer proposal already carried it, and its own risk list conceded the lock-order and schema complexity — disproportionate to a measurement surface with an authoritative store beside it.

**Lock order (stated for the new lock):** supervision file → claims file → telemetry file, telemetry innermost; the telemetry flock is never held while acquiring any other lock. Asserted in the T4/T5 tests.

**Line schema:**
```json
{"schema_version": 1, "kind": "authority|claim", "action": "merge|consult",
 "decision": "permitted|denied", "transition": "minted|executing|executed|cancelled|reconciled|parked",
 "reason": "<str>", "campaign": "<id>", "project_root": "<path>", "issue": 963, "pr": 970,
 "claim_id": "<id>", "revision": 4, "supervision_state": "away", "load_status": "valid",
 "session": "<CLAUDE_CODE_SESSION_ID or null>", "ts": "<iso Z>"}
```
`kind` discriminates which of `decision`/`transition` is present. Reader: none shipped here (measurement is ad-hoc jq/python, like the 2026-08-06 zero-callers analysis) — a reader CLI is a named non-goal.

## 6. Security implications

- The broker is the sanctioned executable merge path, and it enforces fail-closed WITHIN its own invocation. **Enforcement-boundary honesty (pass-2 High, adopted as wording):** what routes campaign merges INTO the broker is prose pinned by guard tests — the same enforcement layer every WF gate in this plugin uses — not an executable block on raw `gh pr merge`. That hard block (PreToolUse) is the issue's own named follow-up. Until it lands, a prose-violating session can still run the raw command; the guard tests make silent prose regression impossible, and the follow-up closes the rest.
- Fail modes, per path (repo convention: a boundary that cannot evaluate fails closed): marker unreadable → deny; supervision state invalid/deleted → deny; driver-state corrupt or governed-but-missing → deny; target binding unprovable → deny; stale-authorization recheck fails → deny; pre-execution telemetry unwritable → abort before side effect; ambiguous merge outcome → park, never blind-retry past one probe-confirmed attempt.
- No new trust boundary: the marker and telemetry live in the same filesystem trust domain as `.supervision.json` itself (the #947 finding-5 refutation applies — an actor who can forge these files already has code-execution in hooks/).
- No secrets touched. `gh` auth is ambient (existing convention). Telemetry lines carry no secret material.
- Injection surface: `--campaign`/`--pr`/`--repo` values reach `gh` argv via the runner (list-form argv, `shell=False` — `launcher_lib.py:1588-1590`); campaign ids are already validated by `validate_campaign_id` (`supervision_lib.py:388`); pr is int-validated by argparse.

## 8. Test design (sketch — Step 5 decomposes)

- **Marker (first, TDD red on the live defect):** declare → `os.unlink(.supervision.json)` → `read_state` returns invalid; `authority_permits("merge")` False; claim mint refused (−1 fence); `consult_check` rc 1; `installs_forbidden` True. Never-declared (no marker) stays attended — `test_absent_state_is_attended_and_permits_everything` gets qualified to the no-marker case, not deleted. Corrupt marker → invalid even with a valid state file. `mark_attended` clears; post-attended deletion → attended. Crash windows, all four: declare-from-attended crash (marker true + valid ATTENDED state → invalid — the pass-1 Critical); declare re-declare crash (marker revision > state revision → invalid); mark_attended crash (marker cleared first → old away record governs, restrictive); marker-live + state-absent → invalid. Recovery revision rule: declare after deletion mints `marker.revision + 1` with pre-existing claims at the old revision still coherent. bootstrap-marker: valid away state → marker true; valid attended → marker false; absent/invalid → no-op.
- **Broker:** fake-runner in-process tests per launcher_lib idiom — target-binding mismatch rc 12 before any authority read; denied (no grant); permitted-attended; permitted-by-grant; foreign-identity claim refusal vs same-identity idempotent resume (pending/executing/executed); clean merge (runner asserts exact argv) followed by the mandatory probe-confirm before mark_executed; probe-unconfirmable success → ambiguous path, never recorded; ambiguous timeout → probe MERGED → resolve rc 0; probe OPEN → one retry → rc 0/12; probe unknown → park rc 13; strict-telemetry failure aborts before the runner sees a merge call (rc 12, reason telemetry-unavailable). One real-subprocess CLI test (--help + a refusal path).
- **Telemetry:** every broker path leaves the expected line sequence; torn-tail repair; concurrent append integrity (two processes, no lost line); claims-transition lines from the claims unit suite.
- **Prose guards:** the three location pins of §5.6 + step_state signature tests extended (`tests/hooks/test_step_state_hook.py:73-91`).
- **Pass-2 additions:** the full re-run transition table (pending/executing/parked/executed/cancelled — cancelled re-mints only after fresh binding + authority, `reopened` telemetry line; executed terminal); driver-state hash recheck aborts on mutation between binding and merge; broker self-heals a missing marker for a valid state; the `merge_policy` end-to-end fixture (driver state created exactly as the epic-run prose prescribes → `evaluate_campaign` yields the scoped grant); binding accepts a "Part of #N"-body PR and rejects an unrelated PR; argparse rc-2 exits keep the standard stderr contract.

## 9. Scope + multi-PR assessment

In scope: exactly the issue's five ACs (§2-§5 above) + their tests. Out of scope (issue-named): route_for consumers beyond merge, PreToolUse hard enforcement, attended behavior changes. Estimated diff: ~1200-1500 lines incl. tests — above the 500-line multi-PR flag. **Recommendation: ONE PR**, tasks strictly ordered marker-first (AC2's "FIRST" is satisfied by commit order inside the PR); a split into marker-PR + broker-PR doubles CI cycles during an active GitHub Actions outage and the marker alone is unobservable without the broker's telemetry. Swap-point: if Step 11 review balks at diff size, the marker commits stand alone and can be cherry-picked into a Part-1 PR.

## 10. Failure modes of this design (what is likeliest wrong)

1. The fail-closed pre-execution telemetry gate could brick campaign merges on a full disk — accepted deliberately (rc 12 with a legible reason beats an unrecorded merge), named for the gate to probe.
2. The `"invalid"` mapping might surprise a consumer that treats invalid as "corrupt file present" (e.g. a future repair tool reading the file) — mitigated by the stderr marker-naming warning and telemetry `load_status` field.
3. `mark_attended` semantics under an absent-but-marker-live state: it must clear the marker even though the state file is gone (recovery path, revision `marker.revision + 1`) — verified by a dedicated test.
4. The marker↔state consistency rule (`state.revision < marker.revision` → invalid) is the subtlest new logic — an off-by-one there fail-closes a healthy workspace or fail-opens a crashed declare. All four crash windows carry dedicated tests (§8).
5. Target binding depends on the campaign driver-state recording the child's membership — a campaign whose state predates the queue conventions may deny legitimately-scoped merges (fail-closed direction; the operator re-runs after `record-child-outcome` fixes the state).
6. A marker in the same directory as the state file does not survive a directory-level wipe (`rm -rf claude_docs`) — named residual, out of threat model (an actor with that access can edit hooks/ directly; #947 finding-5 refutation reasoning).
